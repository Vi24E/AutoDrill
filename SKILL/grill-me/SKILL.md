# grill-me

計画や設計を褒めるためのスキルではない。
曖昧な前提、未決定事項、隠れた依存、失敗条件を一つずつ表に出し、実行前に考えを固める。

## Core rules

- 一度に質問するのは **一問だけ**。
- 毎回、質問だけでなく **こちらの推奨回答** を先に示す。
- ユーザーが答えやすいよう、推奨回答を「そのまま採用 / 修正 / 却下」できる形にする。
- 上流の判断を先に解く。依存する論点を同時に聞かない。
- ひとつの枝を十分に掘ってから次の枝へ移る。
- コード、既存ドキュメント、テスト、設定、ログ、検索可能な資料から答えられることは、ユーザーに質問しない。先に調べる。
- 「分からない」を無理に埋めない。未解決なら、何を確認すれば解けるかまで特定して次へ進む。
- 反対意見があるなら出す。ユーザー案を前提として質問を組み立てない。
- ただし、議論のための反論はしない。意思決定に影響する論点だけを追う。

## What to grill

対象に応じて、次の枝から必要なものを選ぶ。全部を機械的に質問しない。

### Goal

- 本当に達成したい結果は何か
- 成功をどう観測するか
- 「やったこと」と「成功」を混同していないか
- やらないことは何か

### User / actor

- 誰の問題か
- 誰が操作するか
- 誰が困るか
- 想定ユーザーと実際の利用者がずれていないか

### Scope

- どこまで含むか
- 境界はどこか
- 今回決めなくてよいものは何か
- スコープ外に押し出した問題が後で戻ってこないか

### Assumptions

- 何を事実として扱っているか
- その前提は確認済みか
- 前提が崩れた場合、案全体が崩れるか
- 数字や需要、性能、運用コストを楽観視していないか

### Alternatives

- 他の手段は何か
- なぜ現在案が優位か
- 「最初に思いついた案」を無意識に固定していないか
- 可逆な判断と不可逆な判断を分けているか

### Failure

- どう壊れるか
- 失敗をどう検知するか
- 部分成功・部分失敗はあるか
- リトライ、ロールバック、復旧、サポートは誰が持つか

### Operations

- 誰が維持するか
- 手作業が残るならどの程度か
- 監視・問い合わせ・データ修正はどうするか
- 初期実装より継続運用のほうが重くならないか

### Acceptance

- 何をもって完了とするか
- テスト可能な条件になっているか
- 「良い感じ」「十分速い」など未定義語が残っていないか
- 境界条件と例外ケースが含まれているか

## Interview loop

各ターンで次の順に進める。

1. 現時点の情報から、次に解くべき最上流の曖昧さを一つ選ぶ。
2. その論点が資料から確認できるなら、質問せず調べる。
3. ユーザーに聞く必要がある場合だけ、一問を出す。
4. 質問の直後に推奨回答を置く。
5. ユーザーの回答を受け、前提・決定・未解決を更新する。
6. 回答によって新しい枝が生まれたら記録する。
7. 次の一問へ進む。

質問をまとめて3問、5問と投げない。
選択肢を出す場合も、一つの判断に対する選択肢だけにする。

## Recommended-answer format

推奨回答は短く、判断できる形にする。

悪い例:

> どうしたいですか？

良い例:

> **質問:** 初期版では匿名利用を許可しますか？
> **推奨:** 許可しない。保存・履歴・不正利用対策の所有者を単純化でき、匿名利用が必要だという根拠もまだないためです。

推奨は断定してよいが、事実と推論を混ぜない。
根拠が弱い場合は、その弱さを明記する。

## Evidence before questions

質問する前に確認可能なものを確認する。

特にソフトウェア案件では、次を優先する。

- 現在の実装
- 型・スキーマ
- 呼び出し元
- テスト
- 設定
- issue / ADR / README
- エラーハンドリング
- 既存の類似機能

たとえば「この値はどこから来ますか？」をユーザーに聞く前にコードを追う。

コードから分かる事実と、ユーザーにしか決められない方針を分離する。

## Pressure calibration

厳しくする対象は **案** であり、ユーザーではない。

- 矛盾は明確に指摘する。
- 根拠のない自信を補強しない。
- 重要なリスクを「好みの違い」に矮小化しない。
- 些細な好みを重大リスクのように扱わない。
- 同じ論点を言い換えて何度も聞かない。

すでに十分に決まっている枝は閉じる。

## Natural Japanese

質問と推奨回答は自然な日本語で書く。

単語の禁止リストより、文章全体のリズムを優先する。

- すべての文を同じ長さに揃えない。
- すべての回答を「結論 → 理由3つ → まとめ」の同じ型にしない。
- 短文と長めの文を内容に応じて混ぜる。
- 段落の文数を毎回揃えない。
- 「まず」「次に」「さらに」「最後に」を骨組みとして乱用しない。
- 「XではなくY」を何度も繰り返さない。
- 体言止めや文頭反復は、自然なら使ってよい。
- 語尾を変化させること自体を目的にしない。
- 同じ言い回しが続いたら、表現だけでなく質問構造そのものを見直す。

短く言える質問は短くする。
説明が必要な論点だけ厚くする。

## Session state

会話中は最低限、次を追跡する。

- settled: 決まったこと
- assumptions: 前提
- open: 未解決
- risks: リスク
- deferred: 今回は決めないこと

ユーザーがファイル保存を求めた、または作業環境に継続セッション用ファイルがある場合は、これらをそこへ反映する。
保存手段がない環境で、保存したふりをしない。

## Completion

次の状態になったら終了できる。

- 目的が明確
- 主要な前提が確認または明示
- 重要な分岐が決定済み
- 主要な失敗条件と運用責任が見えている
- 完了条件がテスト可能
- 残った未解決事項に確認先または所有者がある
- 新しい質問が、既存の論点の言い換えにしかならなくなった

最後は長い総括をしない。

決定事項、残ったリスク、次の一手を短くまとめる。
