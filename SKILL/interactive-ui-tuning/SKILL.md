# Interactive UI Tuning

UIの見た目に主観的な選択が必要なとき、ユーザーが実際に見ながら調整し、その結果だけを保守可能なproduction codeへ反映するためのskill。

変更が数pxの微調整か、大幅な配色変更、枠の形、配置、画面構成の変更かは問わない。

## 発動条件

次のような場合に使う。

- 言葉で何度も指定するより、ユーザーが見ながら選んだ方が早い
- 色、余白、文字、形、密度、強調、配置などに複数の妥当な見た目がある
- 要素の追加・削除や、複数のレイアウト案を比較したい
- 参考画像や既存画面に近づけながら調整したい

単なるUIバグだからという理由では使わない。overflow、壊れた座標計算、誤ったresponsive layout、二重のgeometryなど、客観的に直すべき構造上の問題が原因なら先にその問題を修正する。

## 1. 何を判断したいか確認する

対象の画面、部品、状態、viewportと、見た目の判断に影響するproduction codeを確認する。

最終実装でどこが値や構造の基準になるべきかも把握しておく。ただし、この段階で本番実装を完成させる必要はない。

## 2. 最も扱いやすい調整画面を作る

ユーザーが見ながら判断できるなら、実UIでも一時的なモックでもよい。目的に合う方を選ぶ。

### 実UIを使う場合

実際のcomponentへdevelopment-onlyのcontrol panelや一時的なstateを追加し、見た目をその場で変えられるようにする。

### モックを使う場合

大きなデザイン変更や構造比較では、機能を持たない一時的な画面を作ってよい。見た目の判断に不要な保存処理、network処理、本物のbackend、実際のbutton動作などは実装しない。

ただし、視覚判断に影響する部分は現実的に再現する。実際には長文が入る画面を短いdummy textだけで調整したり、通常は多数の要素が並ぶ画面を空のcardだけで判断したりしない。

## 3. 必要な選択肢を必要なだけ操作可能にする

control数に固定の上限を設けない。今回の判断に関係するものは十分に触れるようにし、関係のないCSS propertyまで並べない。

対象には数値だけでなく、たとえば次も含めてよい。

- 配色や色の組み合わせ
- 枠線、角丸、影、背景
- typography
- spacingとdensity
- 要素の大きさ
- alignmentと配置
- layout方式
- component variant
- 要素の有無
- 複数の画面構成案

slider、number input、select、toggle、preset、直接操作など、判断しやすいcontrolを使う。

調整のためだけに、壊れたlayoutをtranslateや負marginで隠したり、特定routeだけの例外を作ったりしない。

## 4. ユーザーの選択を簡単に返せるようにする

ユーザーに数値や設定を文章へ書き写させない。

基本的には、

1. ユーザーが画面を見ながら調整する
2. 確定する
3. 生成された結果をそのままコピーしてChatへ貼る

だけで済むようにする。

local environmentから選択状態を直接読める場合は、コピー&ペーストすら不要にしてよい。

保存形式は固定しない。JSON、一時ファイル、選択ID、完全な設定文字列など、LLMが選択状態を曖昧なく再現できる一番簡単な方法を使う。

調整画面を渡したら、どこを開くか、何を操作するか、どう結果を返すかだけを簡潔に伝え、ユーザーが決める前に主観的な見た目を勝手に確定しない。

## 5. production codeへ翻訳する

ユーザーが決めた状態は「望ましい見た目の仕様」として扱う。モックやtunerのコードを、そのままproductionへコピーしない。

最終実装では、既存のdesign token、style、component、variant、layout primitiveなど、意味的に正しい責任範囲へ変更を反映する。

ユーザーは見た目を決め、実装側は保守可能な構造へ翻訳する。

## 6. 一時物を削除して検証する

反映後は、調整のためだけに追加したroute、panel、mock、dummy data、endpoint、temporary state、保存処理などを削除する。正式な機能として残す明確な理由がある場合だけ残す。

その後、変更した画面を実際にrenderして確認する。必要に応じて異なるviewport、keyboard focus、text wrapping、overflow、contrastなども確認し、repositoryで要求される検証を通す。

完了時にproduction codeへ残るのは、原則としてユーザーが選んだ結果と、それを正しく支える実装だけとする。
