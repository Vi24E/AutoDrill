# Maintainable Coding

production codeを変更するときの基礎契約。目的は、目の前の例だけを通すことではなく、変更後のコードをより一貫し、理解しやすく、壊れにくい状態にすること。

## 適用範囲

production codeを変更するすべての作業で適用する。調査の深さは作業に比例させる。

小さな変更でも、編集前に少なくとも次を確認する。

- 変更する規則やデータをどのmoduleが担当しているか
- その情報の基準となる実装や定義はどこか
- 既存の再利用可能な実装があるか
- 変更がどこまで影響するか

バグ修正では、症状だけでなく根本原因と破られた不変条件まで確認する。architecture、public API、schema、永続形式などを変える場合は、責任範囲、公開契約、移行後に残る旧経路まで確認する。

調べればコードや文書から分かることを、ユーザーへ質問しない。

## 判断の境界

実装方法は自律的に決める。データ構造、関数分割、名前、標準ライブラリの選択、局所的なアルゴリズムなど、同じ仕様を満たすための技術的選択をユーザーへ逐一確認しない。

ユーザーへ確認するのは、調査してもコードから決められない意味上の選択が残る場合だけとする。たとえば、productの挙動、公開契約、互換性方針、永続データの意味、責任を持つ層などが未決定で、どの案も正当な場合である。

「実装案が複数ある」こと自体は質問の理由にならない。

## 実装

### 最小diffではなく、最小の完結した修正

変更行数を減らすために場当たり的な条件分岐や例外を増やしてはいけない。

原因が共有の定義、データモデル、責任分担、共通primitiveにあるなら、必要な範囲まで跨いで直す。同じ原因を持つ別のケースでも自動的に成立する形を選ぶ。

一方で、原因と無関係なcleanupや別問題の改善まで同じ作業へ広げない。

### 一つの意味には一つの基準

同じ規則、schema、geometry、capability、状態、数学的意味などを複数箇所で独立に管理しない。基準となる定義を一つにし、必要な表現はそこから導出する。

意味論として同じ機能を今後も使い続ける見込みが高いなら、可読性のためにも適切に抽象化する。逆に、意味が異なる機能を、現在たまたま同じ実装だからという理由だけで共通化しない。

将来の仮定だけを理由に過剰な抽象化を作らない。

### 防衛機構は本当の境界を守る

validation、guard、bounds check、authorization、整合性確認などが正常な入力を拒否したとき、特定のcallerだけ無効化したり、根拠なく許容範囲を広げたりして通さない。producerとconsumerの契約、単位、座標系、境界条件、metadata、validator自身の条件を確認し、本来の不変条件を直す。

新しい防衛機構も同様に、本当に守るべき条件を直接表現する。正常な利用を追加するたびに例外やtoleranceの緩和が必要になる仕組みを作らない。inclusive/exclusive、単位、`null`と省略など、重要な境界は曖昧にしない。

### エラーハンドリングも設計の一部

想定できる失敗を握りつぶさない。回復可能な失敗と、不変条件違反のように処理を止めるべき失敗を区別する。

原因を失う形でerrorを空値やbooleanへ潰さず、callerが判断するために必要なcontextを保つ。retryやfallbackは、それが正当な方針である根拠がある場合だけ使う。失敗経路でもresourceのcleanupを保証する。

ユーザー向けのerrorでは内部事情を不要に漏らさず、可能なら次に取れる行動が分かる形にする。

### 読みやすさを優先する

短いコードそのものを目標にしない。domain上の意味、データの流れ、責任範囲が読み取れることを優先する。

不要なwrapperや抽象階層は削るが、行数を減らすために意味を隠したり、巨大な関数へ押し戻したりしない。

コメントはコードを読み上げるために書かない。コードだけでは分かりにくい理由、不変条件、外部制約、責任分担を説明する。

### パフォーマンスは常識的であればよい

明確なボトルネックや性能要件でない限り、micro-optimizationや詳細なbenchmarkを目的化しない。

ただし、容易に避けられる明白な計算量悪化、無駄な全走査、不要なcopy、renderごとの重い再計算、冗長なI/Oなどは導入しない。hot pathでは必要に応じて測定してから最適化する。

## 変更を最後まで完結させる

architecture、public API、schema、責任範囲、serialization形式、基準となる実装を変更した場合、新しい経路を追加して終わりにしない。

不要になった旧実装、旧adapter、compatibility path、stale symbol、古い説明、生成物、test、consumerを同じ作業で整理する。互換性要件が明示されていないのに「念のため」でlegacyを残さない。

実験用script、temporary fixture、debug export、検証用copy、試作component、temporary routeなども、正式な資産として残す理由がなければ削除する。価値のあるものだけ、正式なtest、fixture、toolとして意味を持たせて残す。

Git履歴をarchiveとして使い、production treeを過去実装の保管場所にしない。

public contractやarchitectureを変えた場合は、canonical docsも同じ作業で同期する。

## 検証

変更によって壊れ得る契約や不変条件を特定し、それを直接確認できる最も適切なlevelで検証する。

- 純粋なロジックならunit test
- subsystem間の境界ならintegration test
- serializationなら実際のserialize/deserialize
- UI interactionなら実browser interaction
- layoutなら実render
- filesystemやnetworkの境界なら実際の境界に近いtest

repositoryが必須のformat、lint、typecheck、build、testなどを定めている場合は、それらも別途通す。

バグ修正では可能な限り、修正前なら失敗し、修正後に通る回帰テストを残す。単一の具体例だけでなく、壊れていた意味論的な契約や不変条件を保護する。

testを通すために実装を歪めない。testが誤った内部詳細を固定しているなら、守るべき契約を確認してtest側も直す。

## 完了条件

作業は、少なくとも次を満たしてから完了とする。

- 根本原因または要求された機能が、適切な責任範囲で実装されている
- 不要な特例や二重管理を増やしていない
- 意味的に再利用すべきものは適切に再利用・抽象化されている
- error pathと境界条件が雑に扱われていない
- 不要になったlegacyと一時作業物が残っていない
- canonical docsと実装が矛盾していない
- 変更した契約を直接確認する検証と、repositoryの必須gateが通っている
- 最終diff全体を見ても、変更前よりモデルが複雑になっていない
