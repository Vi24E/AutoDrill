自動生成ドリル plan

目的
- 日本の小1〜中3のカリキュラムに沿った計算ドリルを自動生成する。
- ウェブ上での回答・自動採点と、印刷用プリントの両方に対応する。
- 問題の難易度を、解法に必要な基本操作の重み付き計算量として定義する。
- 小学生でも扱える、キーボード記法に依存しない解答入力UIを構築する。
- 問題生成、採点、印刷、将来のパーソナライズまで再利用できる共通基盤を作る。

基本設計

1. 問題生成
- 各分野に専用の問題生成器を持つ。
- 問題は乱数seedから再現可能にする。
- 解を先に決めて問題を逆生成するなど、不正な問題が生成されにくい方式を優先する。
- 生成後に、答えの正しさ、一意性、難易度、表示可能性を自動検証する。
- 同一プリント内の重複や過度に類似した問題を制御する。

2. effort値
- 人間が定数時間で実行できる基本操作を定義する。
- 例:
    - 一桁の足し算
    - 一桁の掛け算
    - 一桁の大小比較
    - 符号判定
    - 繰り上がり
    - 繰り下がり
    - 数字の転記
    - 約分
    - 通分
    - 逆数の取得
- 問題の標準解法を基本操作へ分解し、操作回数ベクトルを求める。

    n(G)
      = (n_add, n_mul, n_compare, n_carry, ...)

- 学年、単元の学習時期、習熟度に応じた重みを与える。

    effort(G | m) = w(m) · n(G)

- 内部では操作回数をベクトルで保持し、画面上では必要に応じて1つの難易度値として表示する。
- 必要になった場合のみ、計算グラフから機械的に導ける次の値を追加する。
    - 依存関係の最長経路
    - 同時に保持する中間値の最大数
    - 分岐数
- 主観的な「概念負荷」などを直接手入力する方式は避ける。
- 実際の正答率と回答時間を用いて、基本操作の重みを後から校正できるようにする。

3. 解答入力
- 通常の文字列入力を中心にしない。
- ユーザー操作によって、最初から型付き構文木を構築する。
- 小学生に「3/4」「sqrt(2)」「15cm」などの記法を要求しない。
- 画面上の数字、分数、根号、単位、符号などのボタンで入力する。
- 分数ボタンを押した場合は、分子と分母の入力欄を持つ分数構造を挿入する。
- 単位は問題に応じた候補を画面上に表示する。
- 問題ごとに入力可能な解答形式を制限する。

解答構文木の例

- 整数
- 小数
- 分数
- 負数
- 根号を含む数
- 単位付き数量
- 有限集合
- 複数変数
- 座標
- 方程式
- 解なし
- すべての数

4. 入力、正規化、表示の分離
- 入力された構文木
- 採点用に正規化された構文木
- 画面表示用の構文木

を分離する。

例:
- 入力表示は 6/8 のまま保持する。
- 採点時には 3/4 に正規化する。
- 「約分しなさい」という問題では、入力を自動で3/4と表示しない。
- 「値を求めなさい」という問題では、6/8と3/4を同値と判定できる。

5. 採点
- 文字列一致ではなく、正規化された構文木同士を比較する。
- 分野ごとに許される同値性を定義する。
- 例:
    - 整数の一致
    - 有理数としての一致
    - 約分済みであること
    - 根号の簡単化
    - 解集合の順不同一致
    - 単位変換を含む物理量の一致
    - 複数変数の対応関係
- 任意の数式同値判定は目指さず、各分野で扱う式の範囲を制限する。

6. 表示と印刷
- ウェブ回答用画面と印刷用画面を分離する。
- 印刷ではA4レイアウトを前提にする。
- 次を設定可能にする。
    - 問題数
    - 列数
    - 問題間隔
    - 名前欄
    - 日付欄
    - 解答欄の大きさ
    - 問題のみ
    - 問題と解答を別ページ
    - 教師用解答一覧
- グラフや図形は、可能な限りSVGまたは座標データとして保持する。

開発上の原則
- 分野を増やす前に、問題生成、解答構文木、採点、印刷の共通基盤を固める。
- 問題生成器は、正しい問題だけを生成するよう制約を組み込む。
- 生成後の検証はUSERによって行う
- 解答形式は文字列ではなく型として扱う。
- 任意の数式処理ではなく、学習分野ごとに必要な範囲へ限定する。
- UIはキーボードに依存させない。
- 小学生が説明なしでも操作できることを優先する。
- effort値は主観的な難易度ではなく、基本操作の重み付き計算量として扱う。
- 公開後の実測データでeffort値を校正する。
- 対応単元数より、生成品質、操作性、印刷品質を優先する。

実装アーキテクチャ

基本方針
- モジュラーモノリスとして実装する。
- 数学的なドメインロジックはRustで実装する。
- Web UIはTypeScript、React、Next.jsで実装する。
- RustのドメインロジックをWebAssemblyへコンパイルし、ブラウザから利用する。
- UIまで無理にRustへ統一しない。
- 初期段階ではバックエンドとデータベースを持たず、静的Webアプリとして動作させる。
- アカウント、クラウド保存、有料機能が必要になった段階で、Rust、Axum、PostgreSQLによるバックエンドを追加する。

責務の分離

Rust側
- 問題生成
- seedによる問題の再現
- 問題生成条件の検証
- 解答の型付き構文木
- 解答エディタの状態遷移
- 解答の正規化
- 採点
- effort操作回数の計算
- 標準解法と計算手順の表現
- 単位、有理数、根号、解集合などの数学的意味論
- 問題表示に必要な意味的データの生成

TypeScript / React側
- DOMの構築
- ボタン、タッチ、マウス、キーボード入力
- フォーカス制御
- レスポンシブUI
- アクセシビリティ
- 数式、筆算、グラフ、図形の表示
- 印刷用レイアウト
- SEO用ページ
- localStorageまたはIndexedDBへの端末内保存
- Rust/WASMとのデータ受け渡し

境界設計
- Rust内部では、可能な限り型付き構造を使用する。
- ドメインロジック内でHashMap<String, JSON Value>のような非型付きデータを多用しない。
- JSONはRust/WASM、API、保存形式などの境界に限定する。
- RustとTypeScriptの間では、バージョン付きDTOを使用する。
- DTOにはschema_versionを含め、将来の変更に対応できるようにする。
- TypeScript側で数学的な正規化や採点処理を重複実装しない。
- Rust側でHTML、CSS、DOM、表示位置などを直接扱わない。

問題生成
- 問題生成器は、同じ入力に対して同じ結果を返す決定的な処理とする。
- 問題の再現には、少なくとも次を使用する。
    - skill_id
    - generator_version
    - seed
    - generation_settings
- seedだけではなくgenerator_versionも保存する。
- 生成アルゴリズム変更後も、過去の問題を可能な限り再現できる設計にする。
- 問題生成後には、生成器とは独立した検証処理を実行する。
- 問題生成器と問題検証器の責務を分離する。

問題データ
- 問題をHTML文字列として保持しない。
- 問題文、数式、筆算、表、グラフ、図形を意味的なデータ構造として保持する。
- Web表示、印刷、将来のPDFやアプリ表示は、同じ意味データから生成する。
- 問題データには次を含める。
    - schema_version
    - generator_version
    - problem_id
    - skill_id
    - seed
    - prompt
    - answer_schema
    - canonical_answer
    - solution_trace
    - operation_counts
    - metadata

解答エディタ
- 解答エディタは文字列エディタとして実装しない。
- ユーザー操作によって型付き解答構文木を直接構築する。
- UI操作はEditorActionとしてRust側へ送る。
- 例:
    - InsertDigit
    - InsertFraction
    - InsertDecimalPoint
    - InsertNegativeSign
    - InsertRadical
    - InsertUnit
    - MoveNextSlot
    - MovePreviousSlot
    - DeleteBackward
    - Clear
- Rust側はEditorStateとEditorActionから新しいEditorStateを返す純粋なreducerとして実装する。
- DOMフォーカスやアニメーションはTypeScript側で処理する。
- 入力構文木、採点用正規化構文木、表示構文木を区別する。
- 入力途中の未完成状態も型として表現し、不正な文字列として処理しない。

effort
- effort値そのものを問題生成器へ直接埋め込まない。
- まず標準解法を基本操作へ分解し、操作回数ベクトルを生成する。
- 学年、学習時期、習熟度ごとの重みは、操作回数とは別データとして保持する。
- effortは原則として次で計算する。

    effort = operation_counts · effort_weights

- 同じ問題でも標準解法が異なる場合があるため、solution_traceにstrategy_idを持たせる。
- effortの操作種類は、必要性が確認されたものだけを追加する。
- 操作種類を削除または変更する場合に備えて、effortモデルにもバージョンを付ける。

WebAssembly
- drill-coreはブラウザ固有APIへ依存させない。
- drill-wasmは薄い変換層とする。
- drill-wasmには次のような境界関数だけを置く。
    - generate_problem
    - generate_worksheet
    - apply_editor_action
    - normalize_answer
    - grade_answer
    - calculate_effort
- 初期段階では、RustとTypeScriptの間をJSONまたはSerde互換DTOで接続してよい。
- 性能問題が実測されるまでは、複雑な共有メモリ最適化を行わない。
- WASM境界へドメインロジックを置かない。

Web UI
- Next.jsのSEO用静的ページと、Reactのインタラクティブなドリル画面を共存させる。
- SEO用説明文はサーバーまたはビルド時にHTMLとして生成する。
- ドリル部分のみをクライアントコンポーネントとする。
- 数学処理はRust/WASMへ委譲する。
- 解答入力はクリック、タッチ、キーボードのすべてに対応するが、キーボードを必須としない。
- 解答形式ごとに独立した巨大な画面を作らず、共通エディタと入力部品を組み合わせる。

印刷
- 初期段階ではサーバー側PDF生成を行わない。
- 問題データから印刷専用Reactコンポーネントを生成する。
- CSSの@media printとSVGを使用する。
- インタラクティブ表示と印刷表示はコンポーネントを分離する。
- 数学的な意味データと描画部品は共有する。
- Web画面をそのまま印刷する設計にはしない。
- サーバー側PDFは、完全に同一なPDF配布が必要になった場合のみ追加する。

バックエンド
- alpha段階では原則としてバックエンドを導入しない。
- 設定や履歴はlocalStorageまたはIndexedDBに保存する。
- 次の機能が必要になった段階でバックエンドを追加する。
    - アカウント
    - 複数端末同期
    - 学習履歴
    - 教師と生徒の管理
    - 有料機能
    - クラス単位の一括生成
    - サーバー側PDF生成
- バックエンドにはRustとAxumを使用する。
- データベースにはPostgreSQLを使用する。
- SQLアクセスにはSQLxを使用する。
- drill-coreをWASM版とサーバー版の両方から利用する。
- クライアントとサーバーで問題生成や採点ロジックを重複実装しない。

テスト
- 通常の単体テストに加えてproperty-based testingを重視する。
- Rustではproptest等を使用する。
- 最低限、次を検証する。
    - 同じseedから同じ問題が生成される
    - 正解データを採点すると必ず正答になる
    - 生成された問題が指定条件を満たす
    - 答えが一意である
    - 分母が0にならない
    - 正規化が冪等である
    - 禁止された重複が発生しない
    - effort操作回数が負にならない
    - 問題表示データが描画可能である
- 大量のseedに対して生成と検証を行う。
- 不具合が発生したseedは回帰テストとして保存する。
- SVG、筆算、印刷レイアウトにはgolden testまたはsnapshot testを使用する。
- Rust、WASM、TypeScript間のDTOについて契約テストを行う。

開発原則
- マイクロサービス化しない。
- 初期段階からバックエンドを導入しない。
- UIをRustに統一すること自体を目的にしない。
- 数学的意味論はRustへ集中させる。
- ブラウザ固有処理はTypeScriptへ集中させる。
- 一つのリポジトリ、一つのWebアプリ、一つのRustドメインエンジンから始める。
- 抽象化は、複数の具体例が現れてから導入する。
- 将来の可能性だけを理由に過剰な汎用化を行わない。
- crate、trait、DTO、データベースを早期に過剰分割しない。
- 正しさ、再現性、テスト可能性を性能最適化より優先する。
- 実測上の問題が確認されるまでWASM境界の最適化を行わない。
